# Curator moves and residual clearing

Curators can record SPN operational moves independently of preparation, clearing, receiver availability, the proposed section or destination, fixed-housing and verified-item workflow routing, Sikh display holds and preparatory transfers. These records remain separate from reviewed plans and source evidence. All vitrine numbers in the museum layout are available as alternative destinations, including special-housing and future-labelled cases.

Keep authorization, the current source-to-saint binding and source evidence revision, current physical revision/version, valid museum location identifiers, request idempotency and audit history. Assistant permissions remain limited to confirming their authorized existing recommendations. Choosing a different destination remains a curator action. A physical confirmation does not rewrite the proposal or the external source.

Bulk clearing reads current physical state and effective proposals inside the serializable save transaction. Preserve confirmed occupants at their effective destination, conservatively preserve confirmed occupants whose destination is missing, and preserve submitted records already confirmed elsewhere or in staging. Stage only the remaining current contents, and require every remaining occupant to be represented. An unrelated unlinked physical holding cannot silently disappear. These protections also apply when an old client submits a record already placed later.

The existing request fields remain supported. The result and audit receipt add `residualClearing`: `stagedCount`, `preservedCount`, `preservedSourceIds`, and `emptyCaseClaim: false`. Preserved IDs include protected occupants omitted by the client. A zero-residual acknowledgement records readiness without changing a location. Repeating the same request returns its original summary. Ordinary residual-clear receipts have top-level `emptyCaseClaim: "none"`; readiness does not establish an empty case or dimensional capacity.

For registered compound observations, an ordinary confirmation automatically records only the selected origin-held pieces in the separate component ledger. It does not relocate the whole source observation, excluded pieces or linked verified inventory items. Existing component locations continue through exact receipt/revision bindings, without special case acknowledgements. New V64 origin-only records do not assert that walking sticks were included; earlier explicit including-sticks evidence remains intact. Component moves and undo advance an effective location version, so stale requests and old shelf annotations cannot revive after a move away and back. Shelf edits are annotations against the selected component location, never moves of other pieces.

Receiver space acknowledgements may survive the source-to-confirmed transition of an approved incoming record already present in that case, with the same source/identity revision, exactly one location-version advance and confirmation after the acknowledgement. Other changes still invalidate that advisory state; invalid availability does not block ordinary filling.

Verification includes domain regressions and a disposable-localhost service test for preparation-independent filling, invalid availability, fixed/verified routing, Sikh destinations, scoped component moves/clearing/shelves/undo, preserved target placements, later moves, zero-residual acknowledgements, replay, source conflicts, clearing/placement race orders and independent-save concurrency. No production repair or data backfill is part of this release.
