# Saved connected-traditions diagrams

Private Vrindavan diagram positions are exploratory visual arrangements. Saving, replacing or deleting them never updates saints, source identities, families, section areas, vitrines, shelves or physical-move confirmations.

`lib/museum-diagram-layouts.ts` exposes readMuseumDiagramLayouts(museumId, actorId), saveMuseumDiagramLayout(input, actorId) and deleteMuseumDiagramLayout(input, actorId). Each returns DiagramLayouts from the shared domain module. Reads require an active database user with museum and full-catalogue access; mutations additionally require manage_museum. Protected server actions must also enforce session access and supply the trusted user id.

Save accepts museumId, current collection revision, optional id (absent creates), name and positions of known section node IDs with normalized center coordinates in [0,1]. Optional areaRevision records proposal origin; it never grants permission or changes actual destinations. Each stored layout includes schemaVersion, graphVersion, update time and actor. Original connections and Current museum proposal are reserved built-in names. Names are unique ignoring case, up to 80 characters, and collections are limited to 30 layouts. New approved subsection nodes are accepted without inventing graph connections.

Storage uses the latest museum-specific MuseumDiagramLayouts AuditEvent snapshot. Each mutation appends an auditable full before/after JSON collection in one Serializable transaction, protected by a museum-specific advisory lock and the exact collection revision. Malformed stored snapshots fail closed rather than being overwritten. No migration or environment variable is required. This deliberate small-collection store can later move to a dedicated table if volume warrants it; it should not be used for physical inventory.

The live built-in museum proposal uses existing PlannerData.areas (MuseumSectionSpacePlan sections, vitrines and versions), not individual saint Planned rows and not a frozen research file. UI geometry and badges must distinguish multi-vitrine, shared and unassigned areas. Saved diagrams retain their original coordinates as proposal areas change; the built-in view can rebuild from current data.

Verification: domain tests cover input bounds, unknown/duplicate IDs, unrelated-field rejection, duplicate names, missing update IDs, collection capacity and provenance. dev:check validates integration types. Real PostgreSQL concurrency requires integrated environment verification; do not claim synthetic adapter tests establish production behavior.
